## 一、本轮目标与非目标

**目标**：把客户端 runtime 收归单一 Swift CapsWriter.app，完成阶段 A 能力边界的全部代码：App 骨架（菜单栏+Dock 策略）、ServiceManager 托管 ASR server、ASR WS client、AudioEngine、ShortcutEngine、Result Pipeline（四段）、FocusManager/PasteInjector/ClipboardPolicy、编辑框迁移（v2 契约不变）、annotation 采集、热词 private helper、client-config.json 配置入口、词库 Swift 直读写。构建通过、可自动验证项全部通过，产出阶段 B/C 验收计划书。

**非目标（本轮不做）**：旧物清理与完整切换（验收通过后）；ASR 调优与热词算法改动；Streaming；DMG 与用户数据目录迁移；设置页详细条目专项；界面四页规格调整；首次打开引导 UX；CLI 桥接。

**全程红线**：不碰 `hot*.txt` 词库内容；不碰服务端推理链路；不碰用户运行中的进程；不做过渡方案；新代码附详细中文注释；桌面安全规则遵守（阶段 B 窗口已报备）。

### 2.2 热词 helper 协议（stdin/stdout JSONL，定稿）

- 进程形态：`.venv/bin/python -m core.client.hotword_helper`（新文件，薄包装现有热词链，算法零改动）；App 启动时拉起，随 App 退出；崩溃由 App 侧重启（退避）。
- 传输：stdin/stdout，每行一个 JSON 对象（UTF-8，`\n` 分隔）。
- 启动握手：helper 就绪后向 stdout 写 `{"type":"ready","version":1}`；App 未收到前不发业务请求。
- 业务请求：`{"id":<int>,"op":"correct","text":"<raw_text>"}`
  响应：`{"id":<int>,"ok":true,"corrected":"<文本>","matches":[{"src":"...","dst":"...","score":0.93}]}`。
  helper 内部顺序对齐现状（`result_processor.py:264-272`）：先 `PhonemeCorrector.correct(text, k=10)`（受 `hot` 门控，返回 `CorrectionResult(text, matchs, similars)`，`matchs` 为 (原词,热词,分数) 三元组，注意字段名拼写就是 `matchs`），再 `RuleCorrector.substitute(...)`（受 `hot_rule` 门控，规则替换无匹配详情返回）。响应 `matches` 只承载 phoneme 命中；`corrected` 为两步后的最终文本。
  失败：`{"id":<int>,"ok":false,"error":"<消息>"}`——App 侧降级为 corrected=raw。
- 控制 op：`ping`（健康探针）、`shutdown`（优雅退出）。词库重载不靠消息：helper 内部对 hot*.txt 做 mtime 轮询自动 reload（复用现有 watchdog 逻辑的同款语义，但不依赖客户端进程）。
- 超时：App 侧单请求 2s 超时，超时按降级处理并记录状态。
- matches 结构用于结果四段保留中的 hotword_matches 字段；具体字段名以现有 `core/client` 热词链实际产出为准，子 agent 先读代码再落协议适配。

### 2.3 client-config.json（最小字段集，定稿）

- 路径：`~/.capswriter/state/client-config.json`（与 status.json 同目录；用户数据目录迁移属 DMG 阶段）。

### 2.4 音频与 WS 线格式（定稿，服务端零改动；以下均为代码事实）

- **消息形态**：全部为 JSON 文本消息，无二进制帧。客户端→服务端为 `AudioMessage`（`core/protocol.py:15-56`）：`task_id`、`source`('mic')、`data`(**base64 编码音频**)、`is_final`、`time_start`、`seg_duration=15.0`、`seg_overlap=2.0`、`context`、`language`。**无独立首帧**，每条消息重复携带全部字段；language/context 取自配置。
- **音频编码**：16kHz mono **float32 小端**原始 PCM，base64 后入 `data`（现状：48kHz float32 采集 → `[::3]` 抽稀 + `mean(axis=1)` 混声道，见 `recorder.py:168-170`）。**20ms 一包 = 320 采样 × 4 字节 = 1280 字节原始**。
- **结束标记**：`data=''` 且 `is_final=true` 的 AudioMessage（`recorder.py:219-229`）。
- **起录阈值缓存**：前 0.3s（`Config.threshold`）音频块先缓存，越阈后与当前块拼接发送（`recorder.py:128-150`），首包约含 0.3s+ 音频；Swift 端需复刻此语义。
- **服务端→客户端**：仅 `RecognitionMessage`（`core/protocol.py:59-113`：`task_id/is_final/duration/time_start/time_submit/time_complete/text/text_accu/tokens/timestamps`）；mic 链路丢弃 `is_final=False` 中间结果（`result_processor.py:252-253`）；服务端无任务开始/错误消息类型。
- **Swift 侧实现要求**：AVAudioEngine 设备格式 → 重采样 16k + 混 mono + float32 小端 → 20ms/1280B 组包 → base64 → AudioMessage JSON。**严禁**改变包大小与节流语义（9-19 节拍事故教训：服务端 WorkHandler 节拍围绕 20ms 块调优）。
- ASRClient 连接参数对齐现状：`ws://127.0.0.1:6016`、`subprotocols=["binary"]`、`max_size=None`、无限重连指数退避（上限 5s）。
- 阶段 B 文件注入旁路：从文件解码为 16k float32 PCM 后进入同一组包发送链（等价于现有 `file_transcriber.py` + `media_tool.py` 的 ffmpeg `f32le/ac 1/ar 16000` 路径，但 Swift 侧可用 AVAudioFile/AVAudioConverter 直接解码 wav；mp3 可经 afconvert 预转）。

## 四、执行流程

1. 主会话为 T1–T10 各建 worktree（父目录平铺 `../CapsWriter-Offline-wt-T<N>/`，分支 `wt/T<N>-<slug>`，自 `fc3e75c` 切出）。
2. 按任务卡分派子 agent（白名单互不相交，可全并行）；每个子 agent 交付：代码 + worktree 内 `swift build` 通过证据 + 自验命令输出。
3. 主会话逐个 review diff（对照任务卡逐条核对、亲自跑构建取证），合并回主工作区；冲突由主会话解。
4. 主会话做接线集成；跑 `bash tools/build_dashboard.sh` + `swift run --package-path native/CapsWriter DashboardCoreChecks`。
5. 产出《阶段 B/C 验收计划书》，邀请用户进入阶段 B（用户离开前授权三弹窗 + 停旧 server）。

## 五、三阶段验收（骨架，完整版在阶段 A 收尾时产出）

- **阶段 B（无人值守，6016）**：ServiceManager 真实拉起 server（模型加载/就绪/内存/崩溃退避/强杀恢复）；文件注入全链路（evals 音频→PCM→WS→raw→helper→corrected 断言）；TextEdit 真实焦点/Paste/changeCount 四组合矩阵；Dock 与菜单栏 AX 断言+截图；hidutil 残留检查。

## 六、风险与回退

- 音频节拍耦合（2.4 已定防呆：严格 20ms/1280B/float32/base64 JSON，复刻 0.3s 起录缓存语义）；Fn 键 Globe 冲突（设置流程内引导，阶段 C 验证）；helper 协议与现有热词产出字段的出入（T7 先读代码再落适配，字段名 `matchs` 为现状拼写）；v2 契约字段兼容性（T6 golden 对照 evals/manual_cases/v2 现有 200 行 + 190 个 mp3）。
- 上屏行为变化属有意改变：macOS 现状不恢复剪贴板（`restore_clip` 实际无效），新版按定稿 changeCount 安全恢复——阶段 C 四组合矩阵重点验收。
- 服务端只有 RecognitionMessage 一种下行消息、无错误帧；ASRClient 的错误感知只能靠连接状态与超时，不发明新协议。
- 回退：全部施工在分支与 worktree 进行，主工作区旧代码路径不动；任何时候 `git checkout fc3e75c` 即回基线；用户日常链路全程可用。
